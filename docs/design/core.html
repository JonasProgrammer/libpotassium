libpotassium

Core types and authenticated-encryption contracts

potassium.core defines the types used by SecretBox, AEAD, Box, Ed25519 and X-Wing. Each construction supplies its own algorithm tags, trait specializations and operations.

Key, nonce and MAC types

Material Owner Read-only view Extent in bytes
Confidential key secret_key<KeyTag> or caller-selected storage key_ref<KeyTag> key_traits<KeyTag>::size
Public key public_key<A> public_key_ref<A> algorithm_traits<A>::public_key_size
Nonce nonce_buffer<A> nonce_ref<A> algorithm_traits<A>::nonce_size
Detached MAC mac_buffer<A> mac_buffer<A> const& algorithm_traits<A>::mac_size

A confidential key tag identifies its cryptographic purpose and needs only a key_traits specialization. An algorithm tag identifies a construction, and its algorithm_traits specialization supplies the dimensions and message limit applicable to that construction. The public-key owner and view need only the public-key dimension from those traits. Distinct key purposes and algorithms remain distinct types even when their byte lengths match.

Each key and nonce view takes an explicit std::span<const std::byte, N> and borrows the underlying bytes. A matching owner converts implicitly to its view on lvalues only. Both mutable and const rvalues must reject borrowing, including through named view accessors. The caller keeps the backing storage alive for every use of the view and controls the protection and wiping of externally owned secrets.

Public keys and nonces are ordinary copyable, movable values with fixed-size inline byte storage. A public key carries the full algorithm identity, so reusing the same encoding across protocols requires explicit adaptation. Constructing a public-key view establishes its extent and declared type only. Peer identity and acceptance of the encoded key are separate questions. A detached MAC is a copyable, algorithm-typed value in ordinary memory. Check the received MAC length against its extent and copy its bytes into mac_buffer<A>::storage or the writable, fixed-extent span returned by bytes().

Confidential storage

Operations borrow confidential keys independently of the storage policy. The default heap owner stores a key-sized byte array in std::indirect using the guarded allocator. Moving the owner transfers the allocation without copying key bytes. Move assignment wipes and releases the destination’s previous allocation. Borrowing requires a live allocation, so a moved-from owner must receive a new allocation before it can be borrowed from. A stack-local key_buffer_storage<KeyTag> owns a fixed-size buffer, disallows copying and moving, and wipes its contents on destruction. Generate or derive keys directly in their final writable storage and make any duplication explicit. Default construction of either confidential owner requires a default-constructible key_traits<KeyTag>::generator satisfying KeyGenerator<G, KeyTag>. Size-only key traits support explicit generator, zero, and for_overwrite construction.

Guarded allocation attempts page locking on a best-effort basis. Stack storage does not acquire a lock automatically because disjoint objects may occupy the same page. Callers requiring strict locking can guard a contiguous aggregate with mlock_guard when they control all affected pages.

Decrypted plaintext uses a move-only secure_buffer backed by guarded allocation. Destruction, shrinking and reallocation must wipe secret bytes before their storage becomes unused or is released.

Message and operation conventions

Inputs use std::span<const std::byte> and caller-owned destinations use std::span<std::byte>. For SecretBox and public-key Box, combined ciphertext is exactly MAC || encrypted plaintext, with length equal to the plaintext length plus mac_size. For AEAD, combined ciphertext is encrypted plaintext || MAC, with the same length formula. Applications transport the nonce separately and define framing, versioning, replay detection and ordering.

seal(plaintext, nonce) Ciphertext vector

seal_into(plaintext, out) Generated nonce
seal_into(plaintext, out, nonce) Writes combined ciphertext
open_into(ciphertext, out, nonce) Writes authenticated plaintext

Detached operations return or accept the MAC separately. Their ciphertext is exactly as long as the plaintext, including zero bytes for an empty message.

Operation after the key arguments Result
seal_detached(plaintext, nonce) detached_ciphertext<A> with ciphertext and MAC
seal_detached(plaintext) detached_seal_result<A> with ciphertext, MAC and nonce
seal_detached_into(plaintext, out, nonce) Writes ciphertext and returns the MAC
seal_detached_into(plaintext, out) Writes ciphertext and returns detached_mac_nonce<A> with MAC and nonce
open_detached(ciphertext, mac, nonce) Authenticated plaintext in a secure_buffer
open_detached_into(ciphertext, mac, out, nonce) Writes authenticated plaintext

For constructions supporting randomly generated nonces, sealing without an explicit nonce uses the secure RNG, also available through generate_nonce<A>(). Algorithm traits may disable that capability with static constexpr bool random_nonce_enabled = false. To import a nonce, explicitly construct its owner from a fixed-extent byte span. An explicit nonce must be unique for each encryption under the same key across participants, processes and restarts.

Encryption requires plaintext length at most algorithm_traits<A>::messagebytes_max. For the allocation-free message operations, output must be disjoint from every input and sized exactly for the result. Combined opening rejects ciphertext shorter than mac_size before subtracting the overhead to determine the output size. Failed authentication must never expose unauthenticated plaintext.

Failures and implementation boundaries

The default overloads throw crypto_error for cryptographic failure and std::bad_alloc for allocation failure. A final std::nothrow_t selects a nonthrowing overload returning std::expected<T, errc>, including T = void. Malformed ciphertext and backend rejection map to errc::crypto_failed without guessing whether the key, nonce or message was wrong. Allocation failures in ordinary and guarded storage map to errc::allocation_failed.

Core owns the shared RNG, wiping, guarded memory, byte-pointer adapters and error translation. The design keeps libsodium headers, dispatch and backend assertions in private implementation units, with exported interfaces limited to declarations, layouts, constants and short template definitions. Concrete typed key parameters allow an owner to convert to a view during overload resolution. The AEAD templates select their algorithm by borrowing a view through a concrete typed overload.

Shared contract tests cover explicit raw-span construction, lvalue-only borrowing, tag isolation, owner copy and move semantics, and wiping. Each construction exercises both nonce modes, exact output sizes, empty and binary messages, authentication failures and short ciphertext in both error interfaces, including allocation failure where injection is practical.
